# K41: why some CUDA kernels could not be launched ("invalid device function") — root cause and fix

- **Date:** 2026-11-04
- **Question:** Why do `BitVoxelMap::collideWith(map, threshold, offset)` / `ProbVoxelMap::collideWith`, `insertSensorData` and some other `BitVoxelMap` operations fail with `invalid device function` in the CUDA build of this machine, although the device image is valid? (K41, open since 2026-11-03; the user asked for a statically traceable cause: "muss ja statisch nachvollziehbar sein".)
- **Status:** final. Root cause found and fixed; the parity scenario 3 (map x map collisions) and the sensor data work are unblocked by it. Method of the parity work: [2026-11-03_cuda_parity.md](2026-11-03_cuda_parity.md).

## Answer in one paragraph
The kernel *definitions* in `voxelmap/kernels/VoxelMapOperations.hpp` had top-level `const` on by-value parameters (`const uint32_t voxelmap_size`) that the *declarations* in `VoxelMapOperations.h` did not have. nvcc builds a helper template `__wrapper__device_stub_<kernel>` from both; the two forms are different templates (the helper takes its parameters by reference: `uint32_t&` vs `const uint32_t&`). The real launch code is supplied as an explicit specialization of the form built from the declaration, but the host function of the kernel passes `const` lvalues and therefore binds to the *primary template of the definition*, which is a placeholder body: `cudaLaunchKernel(0, 0, 0, 0, 0, 0)`. That call returns `invalid device function`. The fix is to make declaration and definition agree (the `const` was removed from the definitions).

## Evidence (all measured 2026-11-04, MSVC 14.44, CUDA 12.8)
1. **The host function of the kernel was a stub that launches nothing.** The external function `kernelCollideVoxelMapsDebug<Bit,Bit,DefaultCollider>` in `VoxelMap.cu.obj` is 0x69 bytes long and calls `cudaLaunchKernel` with `xor ecx,ecx` (function = NULL) and `xor r9d,r9d` (arguments = NULL); in the linked executable it is the same code. A working kernel (`kernelInsertCoordinateTuples`) loads its own address instead.
2. **The generated code says why** (`nvcc --keep`, `VoxelMap.cudafe1.cpp`): the primary template is `template<class Voxel, class OtherVoxel, class Collider> static void __wrapper__device_stub_kernelCollideVoxelMapsDebug(Voxel *&voxelmap, const ::uint32_t &voxelmap_size, ...) { ::cudaLaunchKernel(0, 0, 0, 0, 0, 0);}`; the forward declaration (from `VoxelMapOperations.h`) and the specialization in `VoxelMap.cudafe1.stub.c` have `uint32_t &voxelmap_size` (no const). The specialization exists in the object (a `static` copy with the real `cudaLaunchKernel` call) but nothing calls it.
3. **Everything else was fine, as measured before:** `cudaLaunchKernel(host pointer, ...)` called by hand with the same pointer works, the driver-API launch of the same `CUfunction` works, `cudaFuncGetAttributes` succeeds; only the generated `<<<...>>>` path (host function -> placeholder) fails. This is why 56 of 56 launches failed, why the device image looked valid, and why no linker flag, `-rdc` or loading mode made a difference.
4. **Consequence, not cause: identical code folding.** The placeholder bodies of different kernels are byte-identical, so `/OPT:ICF` (default of a Release link) folded the host functions of `kernelCollideVoxelMapsDebug<Bit,Bit>`, `<Bit,Prob>`, `<Prob,Prob>` and `kernelInsertMetaPointCloud<CountingVoxel>` onto one address; the runtime then reported the attributes of another kernel (35 registers / 2048 bytes expected, 26 / 0 reported). `/OPT:NOICF` separated the addresses and the attributes became right, but the launch still failed (measured), which is what first pointed away from the linker.
5. **Which kernels:** a scan of all object files (`python tools/cuda_stub_check.py objects build/cuda-rel`) found 17 placeholder host functions before the fix: `kernelCollideVoxelMapsDebug` (3 instances), `kernelCollideVoxelMapsBitvector` (2), `kernelShiftBitVector`, `kernelClearVoxelMap` (bit index overload), `kernelInsertSensorData` (2), `kernelInsertMetaPointCloud` (vector of meanings; 3 map types, several objects). Source scan (`python tools/cuda_stub_check.py sources`): exactly the kernels whose definition has a top-level `const` that the declaration lacks (7 names; `kernelCollideVoxelMaps` is the unused old variant).
6. **Why the earlier attempts did not help:** `.cuhpp` includes (a different, real problem: unresolved device calls were removed, but the launch code was never reached), `/OPT:NOICF`, eager module loading and `WHOLE_ARCHIVE` all act after the placeholder was already compiled in.

## Fix (CUDA library of this fork)
- `VoxelMapOperations.hpp`: top-level `const` removed from by-value parameters of `kernelClearVoxelMap` (both), `kernelCollideVoxelMaps`, `kernelCollideVoxelMapsDebug`, `kernelCollideVoxelMapsBitvector`, `kernelInsertSensorData`, `kernelShiftBitVector`, `kernelInsertMetaPointCloud` (`map_dim`); a comment at the top of the first kernel states the rule.
- After the rebuild: 0 placeholder host functions in all 34 CUDA objects (a first version of the object scan also flagged two `kernel_voxelize_start` host launchers of `PointCloudWrapper.cu` because of their `nullptr` argument; the scan now also requires that the only relocation of the function is the `cudaLaunchKernel` call, which a launcher does not have), `<<<>>>` launches of the three collision kernels return `cudaSuccess`, and the earlier golden lines of scenarios 1, 2 and 4 are reproduced byte for byte.
- **Not verified:** why this does not hurt the upstream Linux/GCC builds (not examined; do not assume it is MSVC specific); the `.cuhpp` include changes tried yesterday are not needed and are not in the code.

## Consequences
- These operations never worked in this build: map x map collisions (both map types), `collideWithTypes` of maps, `clearBitVoxelMeaning` of bit maps, `shiftLeftSweptVolumeIDs`, `insertSensorData` (with and without ray caster), `insertMetaPointCloud` with a vector of meanings. Earlier statements "Tested, not parity" for the Vulkan side are not affected; the Vulkan classes never depended on them.
- The map x map offset (K40's last open part) could now be examined and fixed: scenario 3 in the parity page.
- Tooling: `tools/cuda_stub_check.py` finds the defect without a GPU (sources) and in a finished build (objects); run it after changing a kernel signature.
