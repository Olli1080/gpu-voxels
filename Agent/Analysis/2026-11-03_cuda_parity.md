# CUDA parity, first measurement: list x map collisions (and how to build and run CUDA on this machine)

- **Date:** 2026-11-03
- **Question:** Does the Vulkan `BitVoxelList::collide_with*` (slice S7-5) give the results of the CUDA library? Until now the CUDA behaviour was only read from the source (no CUDA on the old machine); the user released parity work on 2026-11-03 ("ja und dann cuda", Q5).
- **Scope / non-goals:** Scenario 1 only: a bit list against a bit map and a probabilistic map, all three forms (`collideWith`, `collideWithTypes`, `collideWithTypeMask`), three thresholds, eleven offsets, seven masks, 441 result lines. No other part of the library was compared yet (the table at the end lists what is still only "Tested").
- **Status:** final for scenario 1; the method is the template for the next scenarios. **Update the same day (user: "fix doch die border in cuda?"):** the border rule of the three CUDA list x map kernels was changed to the per-axis check, so Vulkan now equals CUDA in all 441 lines (section "Border fix in CUDA").

## Method
1. **CUDA build on this machine** (RTX 4090, CUDA 12.8, driver 621.01). Visual Studio 2022 is *not* installed (only VS 18 "2026" with the toolsets 14.44 = VS 2022 17.14 and 14.51). CUDA 12.8 rejects MSVC >= 19.50 (toolset 14.51) and its MSBuild integration is not installed for VS 18, so the Visual Studio generators do not work. Working route: Ninja plus the 14.44 toolset from a developer prompt:
   ```
   call "C:\Program Files\Microsoft Visual Studio\18\Community\VC\Auxiliary\Build\vcvarsall.bat" x64 -vcvars_ver=14.44
   set PATH=C:\Python311\Scripts;%PATH%        (Ninja)
   cmake -S . -B build/cuda-rel -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_TOOLCHAIN_FILE=C:/Code/gpu-voxels/vcpkg/scripts/buildsystems/vcpkg.cmake ^
         -DGVL_BACKEND_CUDA=ON -DGVL_BACKEND_VULKAN=OFF -DGVL_WITH_PCL=OFF -DGVL_WITH_KINECT=OFF -DBUILD_TESTS=ON -DGVL_CUDA_ARCHITECTURES=89
   cmake --build build/cuda-rel --target cuda_collisions_dump
   ```
   `GVL_CUDA_ARCHITECTURES` is new (cache variable, `cmake/Options.cmake`; default `all` as before; every `gpu_voxels` target used a hard coded `all`, which makes nvcc build every architecture). PCL and Kinect are off (no point cloud files needed here). The types form needs no register flag any more (finding 3, fixed). A full build of the library (85 steps, one architecture) takes about 10 minutes; a first Debug build worked the same way (`build/cuda-ninja`).
2. **Same inputs, same calls on both sides:** `tests/cuda_parity/parity_inputs.h` (plain C++: an LCG, voxel centres as points, the content of the maps and the list, the list of calls, the line format). `tests/cuda_parity/cuda_collisions_dump.cu` runs it on the CUDA `GpuVoxels` and prints one line per call into `tests/cuda_parity/golden/collisions_cuda.txt` (log lines filtered). Every call starts with a fresh list because a collision marks the entries.
3. **Vulkan side:** `tests/vulkan/test_cuda_parity.cpp` (`VulkanTest.CudaParityListMapCollisions`) runs the same calls and compares per call four lines: Vulkan, the CUDA golden line, the host model with the three-dimensional offset (`list_collision_model.h`, what the Vulkan classes promise) and the same model with CUDA's linear offset (new flag `linear_offset`, the rule read from `VoxelListOperations.hpp`). Required: Vulkan == model 3D, CUDA == model linear; where both models agree, that means Vulkan == CUDA. The golden file is committed, so the test needs no CUDA.
4. Mutation runner `tools/mutation/mutate_cuda_parity.py` (6 mutations of `list_collide.comp`), log `tools/mutation/logs/cuda_parity.log`.

## Evidence (measured 2026-11-03, CUDA 12.8 Release sm_89 and Vulkan on the same RTX 4090)
- **All 441 lines:** Vulkan equals its model (3D offset); the CUDA output equals the model with the linear offset; both offset rules give different results in 224 of the 441 lines (offsets that leave the map on one axis, or wrap across rows and slices). In the other 217 lines (every call with offset 0, and offsets whose moved voxels all stay inside) **Vulkan equals CUDA exactly**: counts and the OR of the types.
- Covered inside these lines: the default form needs the list voxel and the map voxel occupied (entries with only the FREE bit do not collide: this confirms the S4 correction), the converted threshold rule of `collideWith` (`floatToProbability`) against the raw rule of the types and mask forms (`float(occupancy) >= threshold`, voxels with occupancy 0, 1, 2 exist for that), a bit map voxel with only the FREE bit is not occupied, empty / single bit / FREE bit / bits across words / all-bits masks, the marking of colliding entries does not change the counts.
- **Mutation check:** 6 mutations of the shader (list voxel not inspected, raw rule with the converted level, no shared bit for masks, types not collected, a bounds check that lets x = dim pass, FREE counts as occupied in the bit map): 6 killed. The first run left two alive (no FREE-only map voxel and no prob. voxel with occupancy 0 / 1 in the data); the inputs were extended and the golden file recorded again.

## Border fix in CUDA (changed 2026-11-03, measured)
The three kernels `kernelCollideWithVoxelMap` (default form, types form) and `kernelCollideWithVoxelMapBitMask` in `voxellist/kernels/VoxelListOperations.hpp` now also require `voxelmap::isInsideAfterOffset(id, dimensions, offset)` (new, `voxelmap/kernels/VoxelMapOperations.h`: the voxel moved by the offset lies inside the map on every axis) in front of the old pointer-range check. This is a deliberate change of the CUDA library (upstream: the offset is added to the linear index and wraps across rows and slices); it makes CUDA agree with the Vulkan rule and with what the documentation of the offset promises. Not changed: the offset of the list x list search (`TemplateVoxelList.hpp` `findMatchingVoxels`) and of the voxel map x voxel map kernels (`getVoxelPtr` with an offset): Vulkan has no counterpart, the wrap is still there.
Result: a new CUDA run gives 224 changed lines out of 441 (exactly the lines in which the two rules differed); `tests/cuda_parity/golden/collisions_cuda.txt` is the run of the changed library, `collisions_cuda_unfixed_border.txt` the run of the original. `test_cuda_parity.cpp` now requires Vulkan == CUDA in **every** line, Vulkan == the 3D model, and the original CUDA == the linear model (so the change is exactly the border rule, nothing else).

## Further fixes in CUDA (same day, user: "gerne auch rest fixen")
- **K39 fixed (measured):** `__launch_bounds__(cMAX_THREADS_PER_BLOCK)` on `kernelCollideWithVoxelMap<VoxelType>` (the types form, `VoxelListOperations.h` / `.hpp`) makes the compiler stay within 64 registers. CUDA was rebuilt **without** `-maxrregcount` and the dump is line for line identical to the one recorded with the flag (no more error 701, the types lines carry counts and types).
- **List merge with an offset (measured):** `applyOffsetOperator` (`TemplateVoxelList.hpp`) used to add the offset to the linear id and to the coordinates; an entry leaving the map got a wrong id (wrap across rows) and an underflowed coordinate. Now the id is computed from the moved coordinates, entries that leave the reference map get the largest id, and `make_unique()` (which every merge ends with) drops them. Scenario 2 (`parity_inputs.h` `merge_*`, `VulkanTest.CudaParityListMerge`): a bit list merged into a bit list, 15 offsets (including 16 and -20, which leave the 16^3 map completely, and -15 / 15 which wrap) x with and without a new meaning = 30 calls, one line each (entry count and a hash of the whole list: coordinates and set bits). **Vulkan equals CUDA in all 30 lines.** The behaviour before the change was not run (it was read: wrong ids and coordinates).
- **List x list collisions with an offset:** nothing to fix, CUDA does not support them (`findMatchingVoxels` logs "Offset for VoxelList operation not supported! Result is undefined." and returns); Vulkan has no counterpart either.
- **Voxel map x voxel map collisions with an offset (K41):** not fixed. `collisionCheckWithCounterRelativeTransform` shifts the base pointer of this map by the linear offset and then runs `voxelmap_size` voxels from there, i.e. it reads (and writes the collision mark) outside the allocation for positive offsets and wraps across rows (read from the source, not run). It could not be fixed with evidence: **the kernel `kernelCollideVoxelMapsDebug` cannot be launched in this build at all** (`invalid device function`, 56 of 56 launches, also with offset 0, also with a launch of the kernel directly from the test program, also with the unmodified source). Checked: all 11 CUDA targets are compiled with `-rdc=true` (it is in the compile rule, not in `FLAGS`), the libraries are static and the device link step runs, the kernel exists in the sm_89 image (`cuobjdump --dump-resource-usage`), but its SASS contains `CALL.ABS.NOINC 0x0`, i.e. a device function call that stayed unresolved after the device link (identified later from the relocations of the object file: `BitVoxel<256>::insert`, `BitVoxel<256>::bitVector`, `BitVector<256>::noneButEmpty`, plain `__host__ __device__` members, neither kernels nor Thrust functors; their definitions are in `BitVoxel.cuhpp` / `BitVector.cuhpp` and only the explicit instantiations in `BitVoxel.cu` / `BitVector.cu` provide them to the device link of static libraries). Tried: (1) including `BitVoxel.cuhpp` and `BitVector.cuhpp` in `VoxelMapOperations.hpp`: the kernel then has no unresolved call (0 `CALL` in the object file and in the final image), **but the launch still fails**; (2) `/OPT:NOICF` for the link (identical COMDAT folding could merge the host stubs of the three kernel instances): no change; (3) `CUDA_MODULE_LOADING=EAGER`: no better message; (4) `WHOLE_ARCHIVE` for `gpu_voxels_voxel`: failed in CMake (`/WHOLEARCHIVE:` is passed to nvlink as a file name). Static and runtime findings (2026-11-03, all measured): (a) the **device image is valid**: the linked cubin extracted from the executable loads with `cuModuleLoadData`, `cuModuleGetFunction` finds the kernel, and a `cuLaunchKernel` of `kernelCollideVoxelMapsDebug<Bit, Bit, DefaultCollider>` with 4096 occupied voxels returns the right count (4096), so the kernel and its device calls are fine; (b) the failing launches are exactly those that are launched from code instantiated in `VoxelMap.cu.obj` (`BitVoxelMap` members: `collideWith`, `collideWithTypes`, `clearBitVoxelMeaning`, `shiftLeftSweptVolumeIDs`: error lines in `BitVoxelMap.hpp` and `TemplateVoxelMap.hpp`), while the insert kernels launched from `TemplateVoxelMap.cu.obj` run; (c) `cudaFuncGetName` maps the host pointer to the right device function name, but `cudaFuncGetAttributes` returns 26 registers and 0 bytes of shared memory, neither the linked image (35 / 2048) nor the relocatable object (28 / 0) of that kernel; (d) ruled out: `/OPT:ICF` and `/OPT:REF` (flags checked on the link line), missing `-rdc=true` (all 11 CUDA compile rules have it), names registered in the objects (all three instances are in `VoxelMap.cu.obj`, equal to the device names), `__cudaRegisterLinkedBinary` symbols (every object of the voxelmap library references a symbol that the device link stub defines), the static initializer sections (every `.cu.obj` has them), lazy module loading, the unresolved device calls (see above). Open: why the runtime binds these entities to the wrong module / function; next static steps: compare the fatbin wrapper tables of `VoxelMap.cu.obj` and `TemplateVoxelMap.cu.obj`, try `-dlto`, shared libraries, or compiling the explicit instantiations of `VoxelMap.cu` in `TemplateVoxelMap.cu`. A per-axis version of the kernel was written and compiled (scenario 3 with a host model was ready), then **everything was reverted** because nothing of it could be run; the attempts (1) and (2) are not in the code.

## Findings
1. **Parity (measured, high):** the three collision forms of a bit list against a bit map and a prob. map equal CUDA in all 441 lines once CUDA checks the border per axis (see above). Before that change they equalled it wherever the offset did not leave the map in a wrapping direction (217 of 441 lines), and the original CUDA numbers equalled a model of the linear rule in every line, as predicted.
2. **Offset difference (measured, high; resolved in CUDA):** the original linear rule counted entries whose moved voxel is in another row or slice; with 16^3 voxels that was half of the calls. CUDA was changed (above), Vulkan keeps the 3D rule (decision of S7-5, same as K31). The old behaviour is only in `collisions_cuda_unfixed_border.txt`. Other CUDA kernels with the same pattern are listed above.
3. **CUDA's types form could not launch on the RTX 4090 as built (measured, high; K39, fixed with `__launch_bounds__`, see above):** `collideWithTypes` (bit and prob. map, `BitVoxelList.hpp` lines 137 and 181) fails with `too many resources requested for launch (701)`, the result is a count of 0 and no types, silently (only a log line). Cause: the kernel `kernelCollideWithVoxelMap<VoxelType>(..., BitVectorVoxel* bitvoxel_results)` uses 80 registers per thread (`cuobjdump --dump-resource-usage`) and is launched with 1024 threads (`computeLinearLoad`), 81 920 registers, above the 65 536 of a block. Debug and Release both fail. With `-maxrregcount=64` it works. Upstream probably built for older architectures where this happened to fit.
4. **CUDA counters are 16 bit per block (inferred from the source, not exercised):** the data have at most 320 entries; lists above 65 535 entries per block would wrap. Not tested.

## What was NOT verified
Everything outside the two scenarios: bit list against bit list or octree, the counting list, merges of other list / map types, the primitive arrays (host only, CUDA's own `PrimitiveArray` formulas were read, not run), lists with more than 2^24 entries, large maps, the Debug-only behaviour of CUDA (Debug fails in the types form for finding 3's reason), other GPUs, other CUDA versions. The 16-bit block counters (finding 4). The border fix was run on 16^3 voxels only (the helper uses `uint32_t` ids: maps with more than 2^32 voxels do not exist in CUDA either).
