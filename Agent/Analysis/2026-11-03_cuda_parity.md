# CUDA parity, first measurement: list x map collisions (and how to build and run CUDA on this machine)

- **Date:** 2026-11-03
- **Question:** Does the Vulkan `BitVoxelList::collide_with*` (slice S7-5) give the results of the CUDA library? Until now the CUDA behaviour was only read from the source (no CUDA on the old machine); the user released parity work on 2026-11-03 ("ja und dann cuda", Q5).
- **Scope / non-goals:** Scenario 1 (the first and largest): a bit list against a bit map and a probabilistic map, all three forms (`collideWith`, `collideWithTypes`, `collideWithTypeMask`), three thresholds, eleven offsets, seven masks, 441 result lines; later added: list merges with an offset (2), voxel map x voxel map collisions with an offset (3), probabilistic map inserts (4), sensor data with ray casting and the robot cut (5). No other part of the library was compared yet (the table at the end lists what is still only "Tested").
- **Status:** final for scenario 1; the method is the template for the next scenarios. **Update the same day (user: "fix doch die border in cuda?"):** the border rule of the three CUDA list x map kernels was changed to the per-axis check, so Vulkan now equals CUDA in all 441 lines (section "Border fix in CUDA"). **Update 2026-11-04:** K41 solved ([root cause](2026-11-04_k41_kernel_stub_placeholder.md)), scenario 3 (voxel map x voxel map collisions with an offset) added, K43 found and fixed (section "Scenario 3"). **Update 2026-11-04 (later):** scenario 5 (sensor data: ray casting and the robot cut) added and compared, K44 found and fixed in CUDA (section "Scenario 5").

## Method
1. **CUDA build on this machine** (RTX 4090, CUDA 12.8, driver 621.01). Visual Studio 2022 is *not* installed (only VS 18 "2026" with the toolsets 14.44 = VS 2022 17.14 and 14.51). CUDA 12.8 rejects MSVC >= 19.50 (toolset 14.51) and its MSBuild integration is not installed for VS 18, so the Visual Studio generators do not work. Working route: Ninja plus the 14.44 toolset from a developer prompt:
   ```
   call "C:\Program Files\Microsoft Visual Studio\18\Community\VC\Auxiliary\Build\vcvarsall.bat" x64 -vcvars_ver=14.44
   set PATH=C:\Python311\Scripts;%PATH%        (Ninja)
   cmake -S . -B build/cuda-rel -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_TOOLCHAIN_FILE=C:/Code/gpu-voxels/vcpkg/scripts/buildsystems/vcpkg.cmake ^
         -DGVL_BACKEND_CUDA=ON -DGVL_BACKEND_VULKAN=OFF -DGVL_WITH_PCL=OFF -DGVL_WITH_KINECT=OFF -DBUILD_TESTS=ON -DGVL_CUDA_ARCHITECTURES=89
   cmake --build build/cuda-rel --target cuda_collisions_dump
   ```
   `GVL_CUDA_ARCHITECTURES` is new (cache variable, `cmake/Options.cmake`; default `all` as before; every `gpu_voxels` target used a hard coded `all`, which makes nvcc build every architecture). PCL and Kinect are off (no point cloud files needed here). The types form needs no register flag any more (finding 3, fixed). A full build of the library (85 steps, one architecture) takes about 10 minutes; a first Debug build worked the same way (`build/cuda-ninja`).
2. **Same inputs, same calls on both sides:** `tests/cuda_parity/parity_inputs.h` (plain C++: an LCG, voxel centres as points, the content of the maps and the list, the list of calls, the line format). `tests/cuda_parity/cuda_collisions_dump.cu` runs it on the CUDA `GpuVoxels` and prints one line per call into `tests/cuda_parity/golden/collisions_cuda.txt` (log lines filtered). Every call starts with a fresh list because a collision marks the entries.
3. **Vulkan side:** `tests/vulkan/test_cuda_parity.cpp` (`VulkanTest.CudaParityListMapCollisions`) runs the same calls and compares per call four lines: Vulkan, the CUDA golden line, the host model with the three-dimensional offset (`list_collision_model.h`, what the Vulkan classes promise) and the same model with CUDA's linear offset (new flag `linear_offset`, the rule read from `VoxelListOperations.hpp`). Required: Vulkan == model 3D, CUDA == model linear; where both models agree, that means Vulkan == CUDA. The golden file is committed, so the test needs no CUDA.
4. Mutation runner `tools/mutation/mutate_cuda_parity.py` (6 mutations of `list_collide.comp`), log `tools/mutation/logs/cuda_parity.log`.

## Evidence (measured 2026-11-03, CUDA 12.8 Release sm_89 and Vulkan on the same RTX 4090)
- **All 441 lines:** Vulkan equals its model (3D offset); the CUDA output equals the model with the linear offset; both offset rules give different results in 224 of the 441 lines (offsets that leave the map on one axis, or wrap across rows and slices). In the other 217 lines (every call with offset 0, and offsets whose moved voxels all stay inside) **Vulkan equals CUDA exactly**: counts and the OR of the types.
- Covered inside these lines: the default form needs the list voxel and the map voxel occupied (entries with only the FREE bit do not collide: this confirms the S4 correction), the converted threshold rule of `collideWith` (`floatToProbability`) against the raw rule of the types and mask forms (`float(occupancy) >= threshold`, voxels with occupancy 0, 1, 2 exist for that), a bit map voxel with only the FREE bit is not occupied, empty / single bit / FREE bit / bits across words / all-bits masks, the marking of colliding entries does not change the counts.
- **Mutation check:** 6 mutations of the shader (list voxel not inspected, raw rule with the converted level, no shared bit for masks, types not collected, a bounds check that lets x = dim pass, FREE counts as occupied in the bit map): 6 killed. The first run left two alive (no FREE-only map voxel and no prob. voxel with occupancy 0 / 1 in the data); the inputs were extended and the golden file recorded again.

## Border fix in CUDA (changed 2026-11-03, measured)
The three kernels `kernelCollideWithVoxelMap` (default form, types form) and `kernelCollideWithVoxelMapBitMask` in `voxellist/kernels/VoxelListOperations.hpp` now also require `voxelmap::isInsideAfterOffset(id, dimensions, offset)` (new, `voxelmap/kernels/VoxelMapOperations.h`: the voxel moved by the offset lies inside the map on every axis) in front of the old pointer-range check. This is a deliberate change of the CUDA library (upstream: the offset is added to the linear index and wraps across rows and slices); it makes CUDA agree with the Vulkan rule and with what the documentation of the offset promises. Not changed: the offset of the list x list search (`TemplateVoxelList.hpp` `findMatchingVoxels`) : Vulkan has no counterpart, the wrap is still there. The voxel map x voxel map kernel was changed on 2026-11-04 (scenario 3).
Result: a new CUDA run gives 224 changed lines out of 441 (exactly the lines in which the two rules differed); `tests/cuda_parity/golden/collisions_cuda.txt` is the run of the changed library, `collisions_cuda_unfixed_border.txt` the run of the original. `test_cuda_parity.cpp` now requires Vulkan == CUDA in **every** line, Vulkan == the 3D model, and the original CUDA == the linear model (so the change is exactly the border rule, nothing else).

## Further fixes in CUDA (same day, user: "gerne auch rest fixen")
- **K39 fixed (measured):** `__launch_bounds__(cMAX_THREADS_PER_BLOCK)` on `kernelCollideWithVoxelMap<VoxelType>` (the types form, `VoxelListOperations.h` / `.hpp`) makes the compiler stay within 64 registers. CUDA was rebuilt **without** `-maxrregcount` and the dump is line for line identical to the one recorded with the flag (no more error 701, the types lines carry counts and types).
- **List merge with an offset (measured):** `applyOffsetOperator` (`TemplateVoxelList.hpp`) used to add the offset to the linear id and to the coordinates; an entry leaving the map got a wrong id (wrap across rows) and an underflowed coordinate. Now the id is computed from the moved coordinates, entries that leave the reference map get the largest id, and `make_unique()` (which every merge ends with) drops them. Scenario 2 (`parity_inputs.h` `merge_*`, `VulkanTest.CudaParityListMerge`): a bit list merged into a bit list, 15 offsets (including 16 and -20, which leave the 16^3 map completely, and -15 / 15 which wrap) x with and without a new meaning = 30 calls, one line each (entry count and a hash of the whole list: coordinates and set bits). **Vulkan equals CUDA in all 30 lines.** The behaviour before the change was not run (it was read: wrong ids and coordinates).
- **List x list collisions with an offset:** nothing to fix, CUDA does not support them (`findMatchingVoxels` logs "Offset for VoxelList operation not supported! Result is undefined." and returns); Vulkan has no counterpart either.
- **Voxel map x voxel map collisions with an offset:** examined on 2026-11-04, see "Scenario 3" below (K41, [root cause](2026-11-04_k41_kernel_stub_placeholder.md), had made the kernel unusable on 2026-11-03).

## Scenario 3: voxel map x voxel map collisions with an offset (measured 2026-11-04)
`parity_inputs.h` `map_calls()` / `map_sets()`: this map and the other map as bit map or probabilistic map (4 combinations), thresholds 1.0 / 0.5 / 0.0 (two bit maps: 1.0 only), 15 offsets (including 16 and -20, which leave the 16^3 map completely) = 150 calls on fresh maps (a collision marks the voxel of the map the call is made on: the `eBVM_COLLISION` bit, or one occupied update for a probabilistic voxel). A line holds the collision count and a hash of the marked map. The probabilistic maps hold distinct voxels per call (K42) and some voxels at 127, so that threshold 1.0 finds collisions.
- **CUDA change (`kernelCollideVoxelMapsDebug`):** the kernel now receives the dimensions and the offset and applies it per axis (`isInsideAfterOffset`): voxel c of the other map meets the voxel c + offset of this map; a voxel that leaves the map does not collide. Before, `collisionCheckWithCounterRelativeTransform` shifted the base pointer by the linear offset and ran `voxelmap_size` voxels from there: moved voxels wrapped across rows and slices, and for every voxel that left the array the kernel read (and marked) memory outside the allocation.
- **Results (`VulkanTest.CudaParityMapMapCollisions`):** the CUDA run of the changed library equals a host model of the 3D rule in all 150 lines (count and hash of the marked map; 124 lines have collisions). The original kernel (linear offset) was run once for a bit map as the called map (60 lines, `collisions_cuda_unfixed_border.txt`): it equals the host model of the linear rule in all 60 lines, and the change altered 43 of them. For a probabilistic map as the called map the original kernel read outside the allocation (undefined, not recorded). **Vulkan equals CUDA in the 10 lines with offset 0** (all four combinations and all thresholds; Vulkan has no offset for map x map collisions).
- **K43 (found by this scenario, fixed):** `ProbVoxelMap::collideWith(const BitVectorVoxelMap*, ...)` cast the bit map to `TemplateVoxelMap*`, which inside `ProbVoxelMap` is the base `TemplateVoxelMap<ProbabilisticVoxel>`: the bytes of the bit map were read as probabilistic voxels (435 instead of 63 collisions in the test data at threshold 0.5, 0 instead of 22 at 1.0). It now casts to `TemplateVoxelMap<BitVectorVoxel>` as `BitVoxelMap::collideWith` always did; afterwards Vulkan equals CUDA there too.
- **Mutation check:** 4 mutations of the Vulkan shaders `bit_voxel_collide.comp` and `prob_collide.comp` (`mutate_cuda_parity.py` P10-P13, log `tools/mutation/logs/cuda_parity_mapmap.log`): 4 mutations, 4 killed.

## Scenario 4: probabilistic map, insertPointCloud (measured, built from a clean `build/`)
`parity_inputs.h` `prob_insert_sets`: 13 calls on one 16^3 map with the meanings 1, 1, 200, 100, 0, 129, 130, 131, 254, 4, 50, 3 (unknown) and 1 (updates +72, +71, -29, -10, +0, +1, +2, +125, -125, -79, set unknown), 80 points each, **all voxels of one call distinct**. After every call the whole map is compared (counts of unknown / positive / negative voxels, a hash of all 4096 values, a histogram of the values). `VulkanTest.CudaParityProbMap`: **Vulkan equals CUDA after all 13 calls.** Two CUDA runs give identical lines. Mutation check (3 more mutations in `mutate_cuda_parity.py`: upper clamp, swept volume offset, unknown meaning): 3 killed.

**CUDA loses updates when a voxel is hit more than once in one call (K42, measured).** With 80 random points (a few voxels hit twice) the first CUDA call gave 72 for every touched voxel, Vulkan 127 for the doubly hit one; with meaning 0 (-10) CUDA kept -10 where Vulkan had -20. Isolated (`prob dup` lines, `VulkanTest.CudaParityProbMapDuplicatePointsInOneCall`): one voxel inserted twice with +72 gives **72** in CUDA and 127 in Vulkan, one voxel inserted four times with -10 gives **-10** in CUDA and -40 in Vulkan. CUDA applies exactly one update per voxel and call (the update of the kernel is not an atomic read-modify-write; both threads read the old value and write the same result). The runs are repeatable (two runs identical), but the result of a race is not a specification, so Vulkan keeps the sum (Accumulate, the default) or an exact serial order (Atomic / Sequential); no mode reproduces the loss.

## Scenario 5: sensor data, `ProbVoxelMap::insertSensorData` (measured 2026-11-04)
`parity_inputs.h` `sensor_groups()`: **one measurement per call** (CUDA runs one thread per measurement without atomics and every ray visits the sensor voxel, so several rays in one call lose updates, K42, and are not a defined input), a fresh 16^3 map per group, the whole map compared after every call (counts, hash, histogram of the values). 267 calls in five groups: "rays" (80: four sensor poses, hits at voxel centres and at arbitrary positions, with and without ray casting; the map saturates at -127 / +127), "special" (22: hit in the sensor voxel also off centre, neighbour, along an axis, corner to corner in both directions), "outside" (18: hits and poses beyond the upper border, NaN and +inf hits), "negative" (18: see K44) and "robot" (129: a robot bit map with bit 5, bit 7 and bit 40 blocks of 512 voxels; hits inside each block and outside all, cut by bit 5, 7, 40 and by a bit that no voxel has, with and without ray casting, and one ray that crosses the robot but hits outside it).
- **Result (`VulkanTest.CudaParitySensorData`): Vulkan equals CUDA in all 267 lines**, in all three update modes (Accumulate, Atomic, Sequential), with the raw input (after the K44 fix, next point; before it the group "negative" equalled Vulkan only when fed with the coordinates CUDA effectively used). Two CUDA runs gave identical lines; the 636 older lines were reproduced byte for byte by the same program. In the robot group the cut is visible: of 16 calls per bit, the 12 outside the robot change the map, the 4 inside do not (bit 9 without voxels: all 16 change).
- **K44 (found by this scenario, measured, fixed in CUDA on 2026-11-04 on request "CUDA anpassen"):** the original CUDA converted `floor(c / side)` to `uint32_t` on the GPU, which saturates: a **negative coordinate (-inf included) and a NaN sensor pose coordinate became voxel 0 on that axis** and the measurement was used (a hit at x = -0.5 updated the voxel x = 0; a sensor pose of NaN started the ray in voxel 0). A NaN *hit* was dropped (explicit `isnan` check), positive values beyond the border (also +inf, 1e9) were dropped. Vulkan drops everything outside the map, NaN and negative included. **The same happened in `insertPointCloud`** (measured with `pointcloud_edge_points()`, 9 single-point calls: the points with x = -0.5, y = -0.01, z = -inf, NaN x and (-7.5, -7.5, -7.5) each marked a voxel; only the points beyond the upper border were dropped). **Fix:** new `mapToVoxelsOrOutside` (`VoxelMapOperations.h`: negative, NaN and too large coordinates become 0xFFFFFFFF, which no map contains) in the eight kernels that check `coords < dimensions` (`kernelInsertGlobalPointCloud`, `kernelInsertSensorData`, the two voxel map meta point cloud kernels in `.hpp` and the four `DistanceVoxel` / collision kernels in `VoxelMapOperations.cu`). **Voxel lists (measured, same bug, fixed in a second step):** `BitVectorVoxelList::insertPointCloud` of the same 9 points (one per call, fresh list): the original CUDA list held an entry for 5 of them (x = -0.5 -> [0,5,5], y = -0.01 -> [5,0,5], z = -inf -> [5,5,0], NaN x -> [0,9,9], (-7.5, -7.5, -7.5) -> [0,0,0]); the list kernels store the coordinates and `remove_out_of_bounds()` only tests `coords >= dims`, which a voxel-0 coordinate passes. The three MapVoxelID list kernels (`kernelInsertGlobalPointCloud` and the two meta point cloud kernels in `VoxelListOperations.hpp`) now use `mapToVoxelsOrOutside`, whose 0xFFFFFFFF coordinates `remove_out_of_bounds()` drops: all 5 entries are gone (`listneg` lines, `CudaParityPointCloudNegativeCoordinates`). **Morton coded lists (`BitVectorMortonVoxelList`, OctreeVoxelID ids; measured on the user's request "Octree messen"):** the same 5 of 9 points became entries (`GpuVoxels::addMap` does not implement `MT_BITVECTOR_MORTON_VOXELLIST`, "NOT YET IMPLEMENTED", so the dump creates the list directly). The three OctreeVoxelID kernels in `VoxelListOperations.hpp` now use `mapToVoxelsOrOutside` as well; afterwards the 9 `mortonneg` lines equal the `listneg` lines. Vulkan has no Morton list: the test requires Morton == map-id list line by line (before and after the fix) and the map-id list is compared with Vulkan. **The octree (`GvlNTree::insertPointCloud`, measured on the user's request "NTree messen", 14 single-point calls, `octree_edge_points()`):** `kernel_toVoxels` used `static_cast<uint32_t>(c / side)` (truncation, no floor): the 5 negative / NaN / -inf points became voxel 0 on that axis, and a point with -1 < c < 0 (x = -0.25) as well (truncation, where the maps and Vulkan floor to -1 = outside). Beyond the upper side the octree was already right (its grid is 2^14, not 16): x = 16.5 -> voxel 16, 16383.5 -> 16383, 16384.5 and 20000.5 -> dropped, +inf -> dropped. **Fix:** `kernel_toVoxels` (`octree/src/kernel_PointCloud.cu`) uses `floorf` and turns negative, NaN and too large values into 0xFFFFFFFF, which the tree drops like every id above its grid (measured: +inf and 16384.5 were dropped before the change, and the negative points are after it). Afterwards the 14 `octneg` lines equal `Octree::insert_point_cloud` of Vulkan with the raw points (`CudaParityOctreePointCloudNegativeCoordinates`), the original lines equal Vulkan with the saturated points. Observation, not examined: `NTree::extractCubes(std::vector<Vector3f>&)` returns the voxel position plus `m_resolution / 2`, where `m_resolution` is in millimetres (1000): positions are voxel + 500, not voxel + 0.5 voxel (the dump subtracts 500). Not touched: `kernelInsertCoordinateTuples` (integer coordinates, no float conversion), the free space sensor pipeline of the octree. Overall 59 CUDA lines changed through K44 (18 sensor, 9 `pcneg`, 9 `listneg`, 9 `mortonneg`, 14 `octneg`) and all other lines are identical byte for byte (885 before the list step, then the 9 new `listneg` lines were added to the file). The original behaviour is kept in `golden/negative_coordinates_cuda_unfixed.txt`; `CudaParitySensorData` and `CudaParityPointCloudNegativeCoordinates` require: fixed CUDA == Vulkan with the raw input in every line, and original CUDA == Vulkan fed with the saturated coordinates (`cuda_saturated`, `cuda_saturated_point`), so both behaviours stay pinned.
- **Mutation check:** 8 mutations of `prob_ray.glsl` (`mutate_cuda_parity.py` S1-S8: robot cut ignored, wrong bit position, bit always in word 0, robot map looked up at the sensor voxel, ray one voxel short, changed tie rule of the walk, ray casting without the flag, sensor voxel not checked; log `tools/mutation/logs/cuda_parity_sensor.log`): 8 of 8 killed. A first data set with robot bits 5, 7, 9 only could not have killed S3 (all below 32), so the bit 40 block was added before the run.
- **Not compared:** several measurements in one call (K42 makes the CUDA result a race), `insertSensorData` with a robot map of other bit vector lengths, other voxel side lengths than 1, maps larger than 16^3 (long rays), the Vulkan `SensorModel` values other than CUDA's constants (CUDA has no such parameter).


## Findings
1. **Parity (measured, high):** the three collision forms of a bit list against a bit map and a prob. map equal CUDA in all 441 lines once CUDA checks the border per axis (see above). Before that change they equalled it wherever the offset did not leave the map in a wrapping direction (217 of 441 lines), and the original CUDA numbers equalled a model of the linear rule in every line, as predicted.
2. **Offset difference (measured, high; resolved in CUDA):** the original linear rule counted entries whose moved voxel is in another row or slice; with 16^3 voxels that was half of the calls. CUDA was changed (above), Vulkan keeps the 3D rule (decision of S7-5, same as K31). The old behaviour is only in `collisions_cuda_unfixed_border.txt`. Other CUDA kernels with the same pattern are listed above.
3. **CUDA's types form could not launch on the RTX 4090 as built (measured, high; K39, fixed with `__launch_bounds__`, see above):** `collideWithTypes` (bit and prob. map, `BitVoxelList.hpp` lines 137 and 181) fails with `too many resources requested for launch (701)`, the result is a count of 0 and no types, silently (only a log line). Cause: the kernel `kernelCollideWithVoxelMap<VoxelType>(..., BitVectorVoxel* bitvoxel_results)` uses 80 registers per thread (`cuobjdump --dump-resource-usage`) and is launched with 1024 threads (`computeLinearLoad`), 81 920 registers, above the 65 536 of a block. Debug and Release both fail. With `-maxrregcount=64` it works. Upstream probably built for older architectures where this happened to fit.
4. **CUDA counters are 16 bit per block (inferred from the source, not exercised):** the data have at most 320 entries; lists above 65 535 entries per block would wrap. Not tested.

## What was NOT verified
Everything outside scenarios 1 - 5: bit list against bit list or octree, the counting list, merges of other list / map types, the primitive arrays (host only, CUDA's own `PrimitiveArray` formulas were read, not run), lists with more than 2^24 entries, large maps, the Debug-only behaviour of CUDA (Debug fails in the types form for finding 3's reason), other GPUs, other CUDA versions. The 16-bit block counters (finding 4). The border fix was run on 16^3 voxels only (the helper uses `uint32_t` ids: maps with more than 2^32 voxels do not exist in CUDA either).
