# Vulkan viewer: in-process, no second process, no Boost.Interprocess

- **Date:** 2026-11-04. **Request** (user): "vulkan viewer ohne boost ipc". Q6 ("viewer later") is lifted for this part; examples, ROS, Kinect and the URDF robot stay out of scope.
- **Status:** first version, *Tested* (not Parity: there is nothing to compare, the CUDA viewer is a separate OpenGL program that was never built here). Maps, bit lists, probabilistic maps and octrees (deterministic and probabilistic, 2026-11-04, user: "octree") can be shown, and so can primitive arrays (spheres and cuboids, 2026-11-04, user: "weiter mit features") robots (the points of the links in their current pose) and, as named layers of a façade, all of them together (`ViewerScene`).
- **Why in-process:** the CUDA viewer is a second process (`gpu_visualization`, OpenGL) that opens `cudaIpcMemHandle_t` handles passed through Boost.Interprocess shared memory ([visualization_and_ipc.md](visualization_and_ipc.md)). Vulkan has no such handle that the old design could use, and a copy of the voxels through shared memory is slow. Here the viewer lives in the program: it reads the **device buffers of the maps of the same `Context`** directly, so nothing is copied to the host and nothing is shared between processes.

## Parts
| Part | Where | What |
|---|---|---|
| `CubeExtractor`, `CubeBuffer`, `BitPalette`, `ProbDisplay` | `vulkan/Viewer.h`, `src/Viewer.cpp`, `shaders/viewer_extract_*.comp`, `viewer_finalize.comp` | compute kernels turn a `BitVoxelMap`, `ProbVoxelMap` or `BitVoxelList` into a list of cubes on the GPU |
| `VoxelRenderer` | same | graphics pipeline (dynamic rendering, no render pass objects), one indirect draw per `CubeBuffer`; `shaders/viewer_cube.vert/.frag` |
| `OffscreenTarget` | same | colour + depth image with read back of the pixels: tests, screenshots, headless use |
| `CubeExtractor::extract(Octree, OctreeDisplay)` | `vulkan/Viewer.h`, `shaders/viewer_extract_octree.comp`, `Octree::extract_to_device` | octree nodes -> cubes without a host copy, see "Octree" below |
| `CubeBuffer::assign`, `CubeKind`, `extract(PrimitiveArray)` | `vulkan/Viewer.h`, `shaders/viewer_sphere.frag` | primitives (host data) -> cubes or spheres, see "Primitives" below |
| `ViewerScene` | `vulkan/ViewerScene.h`, `src/ViewerScene.cpp` | layers of one `GpuVoxels`, visualization hooks, see "Scene" below |
| `OrbitCamera`, `OrbitController` | `vulkan/OrbitCamera.h` | camera around a target (z up), mouse rotate / pan / zoom as pure maths |
| `encode_png`, `write_png` | `vulkan/ImageFile.h` | PNG writer (stored deflate blocks, no dependency) for screenshots |
| `ViewerWindow` | `vulkan_viewer/` (library `gpu_voxels_vulkan_viewer`, needs GLFW) | window, surface, swapchain, depth buffers, frame loop, input |
| `gvl_viewer` | `vulkan_viewer/src/viewer_main.cpp` | program: demo scene or a point cloud file, window or `--png` |

## Data flow
1. `CubeExtractor::extract(map, palette, cubes)`: one blocking submission: zero the argument buffer, extraction kernel (one thread per voxel / entry, `atomicAdd` on the found counter, write the instance if the slot is below the capacity), barrier, `viewer_finalize` sets `instanceCount = min(found, capacity)` so that an indirect draw never reads beyond the buffer.
2. A `CubeBuffer` holds the instances (32 bytes: minimum corner, edge length, packed colour, padding) and 5 words of arguments (the four words of `VkDrawIndirectCommand` plus the number found). `count()`, `found()`, `dropped()`, `download()` read them back (tests, tools).
3. `VoxelRenderer::record(...)` draws every buffer with `vkCmdDrawIndirect` (36 vertices per cube). The vertex shader reads its instance through the **buffer device address** in the push constants (80 bytes: view-projection, address, shading flag): no vertex buffer and no descriptor set. Faces are drawn without culling, the depth test hides the back faces. The device must have `bufferDeviceAddress` (the octree already needs it); the renderer throws otherwise.
4. Whenever a map changes the program calls `extract` again; nothing else is needed, the window draws what the buffer holds.

## What is shown
- **Bit map / bit list:** a voxel is drawn in the colour of its **lowest meaning with a visible colour**; `BitPalette::defaults()` hides meaning 0 (eBVM_FREE) and gives every other meaning a distinct golden-angle hue; `hide(m)` / `set(m, colour)` change it. Voxel c is the cube [c, c + 1) * side.
- **Probabilistic map:** voxels with a known value (not -128) and a value >= `ProbDisplay::min_value` (default 1 = more likely occupied than free), blue (-127) over green to red (+127).
- **Capacity:** `CubeBuffer(context, capacity)`, 32 bytes per cube; cubes beyond it are counted (`found()`), not stored. The demo uses 4 M cubes (128 MB).
- **Shading:** one fixed directional light (ambient 0.35); `RenderOptions::shaded = false` gives the exact palette colour (tests).
- **Octree** (`OctreeDisplay`): the existing extraction kernels (`Octree::extract_to_device`, the same two pass wavefront as `extract()`, but the 16-byte node records stay in a device buffer) feed `viewer_extract_octree.comp`, which decodes the Morton prefix id of every node into a cube of 2^level voxels per side. Uniform nodes are single big cubes (a full 8x8x8 block is one cube). Deterministic tree: occupied nodes in `occupied_colour` (default orange), free nodes in `free_colour` (default hidden, alpha 0 hides); the host passes a status selection to the extraction so hidden nodes are never emitted. Probabilistic tree: known nodes with occupancy >= `min_value`, gradient colour as for the prob. map. `min_level` (0..13) is a level of detail: a refined node on that level is one cube for its whole subtree (deterministic: occupied if any voxel in it is, else free if any is; probabilistic: the largest occupancy below it). `side_length` 0 = the tree's. `collision_colour` (alpha != 0) draws the nodes with the COLLISION status bit (set by `Octree::collide_with`) in that colour, in both kinds of tree. Propagate pending inserts first. `gvl_viewer --octree [--prob] [--level N]`.
- **Primitives:** `CubeExtractor::extract(PrimitiveArray, colour, CubeBuffer)` turns the host array into cubes ([centre - radius, centre + radius] * side, written with `CubeBuffer::assign`). A buffer has a `CubeKind`: cuboids are drawn as cubes, spheres through a second pipeline (`viewer_sphere.frag`): the cube around the sphere is rasterised, every fragment casts the ray from the eye (new push constant `eye`, 96 bytes now) through its position on the cube and intersects it with the inscribed sphere; a miss is a `discard`, a hit writes the depth of the hit point (`gl_FragDepth`), so spheres and cubes hide each other correctly. The context enables `shaderDemoteToHelperInvocation` for it (glslang turns `discard` into a demote at the Vulkan 1.3 target; mandatory in 1.3). The depth write switches early depth test off for the sphere pipeline only. A camera inside a sphere sees nothing of it.
- **Scene:** `ViewerScene(GpuVoxels&, capacity)` holds named layers (bit / prob. maps, bit lists, octrees, primitive arrays; distance maps and counting lists cannot be drawn) with one `CubeBuffer` each, in the order they were added. `show_map(name, MapStyle)`, `show_primitives(name, colour)`, `remove_*`, `refresh()` (extracts the visible layers again), `toggle_visible(i)`, `buffers()` (what `ViewerWindow::draw` / `OffscreenTarget::render` take), `world_size()`. It registers itself with `GpuVoxels::set_visualization_hooks`, so `gvl.visualize_map("name")` / `visualize_primitives_array("name", force_repaint)` of CUDA code show the layer (first call adds it, `force_repaint` extracts it again; false for a distance map; without a scene both stay false). The scene must not outlive the `GpuVoxels`. The window forwards the keys it does not use itself to `ViewerWindow::set_key_handler` (`gvl_viewer --facade`: keys 1 .. 4 toggle the layers, the spheres move and are re-extracted every frame through `visualize_primitives_array`).
- **Robots:** `CubeExtractor::extract(MetaPointCloud, side, RobotDisplay, buffer)` (kernel `viewer_extract_points.comp`, the points stay on the GPU) draws every finite point of the transformed link clouds of a `KinematicChain` as the cube of the voxel that contains it (`snap_to_voxels`, what the robot occupies in a map of that voxel size) or as a cube of `point_size` metres centred on it; one colour per sub cloud (hue per link by default, `colours` round robin, alpha 0 hides a link). The scene reads the pose at every extraction: `show_robot(name, style)`, then `set_robot_configuration` on the façade and `refresh()` (visible layers) or `refresh_layer(index)` (also hidden ones); `layer_buffer(index)` gives the cubes of any layer. CUDA has no visualize call for robots (it shows them as voxels of a map after `insert_robot_into_map`, which still works here). No meshes: URDF robots do not exist on the Vulkan side yet.
- Missing against the CUDA viewer: robot meshes, the XML configuration (colours per map type; styles are set in code), a text overlay. `GpuVoxels::visualize_map` returns `false` unless a `ViewerScene` registered its hook.

## Window
- `ViewerWindow::context_requirements(base)` initialises GLFW and returns `base` plus the instance extensions GLFW needs, `VK_KHR_swapchain`, `enable_graphics` and a queue family filter (`glfwGetPhysicalDevicePresentationSupport`). The `Context` must be created from it, because the maps and the window share the one device and queue.
- `Context` got for this: `ContextCreateInfo::enable_graphics / instance_extensions / device_extensions / queue_family_filter`, the dynamic rendering feature, `DeviceInfo::graphics`, and `Context::submit` / `present` (serialised with every other use of the queue). Without `enable_graphics` nothing changes (compute-only family preferred as before).
- Swapchain B8G8R8A8_UNORM, FIFO (or MAILBOX / IMMEDIATE with `vsync = false`), two frames in flight with a fence, an image-available semaphore and a command buffer each, one render-finished semaphore per swapchain image, recreated when the window size changes or the swapchain is out of date, nothing drawn while minimised.
- **Finding while building it (validation layer):** the first version used one depth image for both frames in flight; the layout transition of the second frame is a write-after-write hazard against the first one. Now there is one depth image per frame in flight. The offscreen path has no such problem (one submission at a time).
- Mouse: left drag rotates, right / middle drag pans, wheel zooms. Keys: S shading, R / Home home camera (`set_home_camera()`), ESC closes, arrows rotate (with shift they pan), Page up / Page down / + / - zoom (these also while held down); other keys go to `set_key_handler`. `set_title` changes the window title (`gvl_viewer --facade` lists its layers there). `handle_key(key, mods, repeat)` is what the GLFW callback calls and what the tests press. `gvl_viewer --points file.xyz|.pcd|.binvox [--side m] [--prob] [--png out.png --size WxH] [--frames N] [--no-vsync] [--validation]`.

## Build
- CMake option `GVL_VULKAN_VIEWER` (default ON with `GVL_BACKEND_VULKAN`): library `gpu_voxels_vulkan_viewer`, program `gvl_viewer`, test `test_vulkan_viewer_window`; vcpkg feature `vulkan-viewer` = `glfw3`. The viewer **core** (`Viewer.h`, `OrbitCamera.h`, `ImageFile.h`) is part of `gpu_voxels_vulkan` and needs no window system.
- **`boost-interprocess` is no longer a base dependency** of `vcpkg.json` (nothing that is built used it); it moved to the legacy `viewer` feature together with the old OpenGL viewer.

## Not verified / open
- A person has not looked at the live window or used the mouse: the GLFW callbacks (button numbers, cursor, scroll, keys) are not exercised by tests, only the controller they feed. Please try `gvl_viewer`.
- Only the RTX 4090 and Windows were used; no Intel UHD run, no Linux / Wayland, no high DPI handling (the framebuffer size is used, the cursor positions are window coordinates).
- Colour configuration from files and a Pan / zoom with the keyboard are not implemented. The scene is not thread safe and does not notice that a map was deleted from the façade (it keeps the shared pointer); no live window test of `--facade` (a person has not seen the moving spheres).
- The dormant OpenGL + Boost.Interprocess viewer (`packages/gpu_visualization`, `vis_interface`) is untouched and still not built.
