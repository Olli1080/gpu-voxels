# Vulkan DistanceVoxelMap (slice S5, 2026-10-23)

Classes in `gpu_voxels_vulkan` (`DistanceVoxelMap.h`): `DistanceVoxelMap`, `DistanceAlgorithm`, `ParallelBandingOptions`.
Status: **Tested** against an independent brute force reference; **not Parity** (no CUDA run, Q5). Not part of S5 (user: "later"): `exactDistances3D` (brute force to a metric point list), `jumpFlood3D` (approximate), `differences3D`, the manhattan floodfill initialisation (`init_floodfill`), `collideWithTypes` (a no-op in CUDA), offsets.

## Data model
One 32-bit word per voxel with the position of the **nearest obstacle** packed as `x | y << 10 | z << 20` (CUDA `DistanceVoxel`); 1023 in all three coordinates = uninitialised. Hence at most **1023 voxels per axis** (user decision: keep the CUDA format). An obstacle is a voxel that stores its own position. The squared distance of a voxel is computed from its position and the stored obstacle (`squaredObstacleDistance`, `INT_MAX` if uninitialised).
Usage: insert obstacles (points, coordinates, meta clouds, `merge_occupied(ProbVoxelMap)`), `compute_distances(algorithm)`, query (`squared_obstacle_distance`, `obstacle_distance` = truncated root, batch `squared_distances` / `distances` by linear index, `extract_distances(robot_radius)` = int8 free-space map with the CUDA border rules and cap 127, `download_obstacles`).
Because an obstacle is "stores its own position", the computation can be **repeated after inserting more obstacles** (CUDA needs `clearMap` in between; stale foreign sites are ignored / reset, `clear_map()` forgets all obstacles).

## Two algorithms (user decision: both)
| `DistanceAlgorithm` | How | Notes |
|---|---|---|
| `Exact` (default) | three separable passes (z: nearest obstacle per column; y and x: lower envelope of parabolas per line, integer arithmetic after Meijster et al. 2000), one invocation per line | any dimensions <= 1023, no band parameters, deterministic ties |
| `ParallelBanding` | port of CUDA `parallelBanding3D` (PBA, Cao et al. 2010): phase 1 flood along z in `m1` bands (+ inter-band propagate/update), phase 2 stack of proximate points along y in `m2` bands (+ forward pointers, pairwise band merging), phase 3 Voronoi walk with `m3` invocations per line (shared memory), out-of-place transposes between the passes | `ParallelBandingOptions{m1, m2, m3}`; see restrictions below; the kernels keep the NUS licence notice (`shaders/pba_common.glsl`) |
Both give the exact squared distance; among equally near obstacles the stored one is deterministic but unspecified and may differ between the algorithms (tests check that it is an obstacle at the minimal distance). Measured on the Intel UHD (single runs, 128x96x80, 300 obstacles): Exact 29-33 ms, PBA 1/1/1 39-44 ms, PBA 4/4/4 22-28 ms, 8/8/8 19-24 ms, 16/32/16 22-24 ms - bands pay off, plain PBA does not beat the separable pass here.

## CUDA behaviour found while porting (and what the Vulkan code does)
1. **PBA loses obstacles in tall maps** (K26): phase 1 compares `|1023 - z|` for uninitialised voxels (flood backward pass, inter-band propagate, update). For a voxel with `z + distance > 1023` the valid obstacle is replaced by "uninitialised" (e.g. one obstacle at z = 520 in a map of 1022 layers: the upper half of the column becomes uninitialised). Port: uninitialised = infinite distance. Test `DistancePbaKeepsObstaclesInTallMapsWithBands`.
2. **One layer per band gives wrong results**: with `m1 = dim_z` the bottom and the top voxel of a band are the same voxel and the inter-band step keeps only one of its two neighbours. Port: `m1 > 1` needs bands of >= 2 layers (throws). Found by an exhaustive sweep of all band combinations on a 32^3 map (every combination with `m1 = 32` failed, all others passed).
3. `m2` that is not a power of two silently produces garbage (the merge loop halves the band count); invalid band counts only fall back to 1 with a warning for non-divisors. Port: invalid values throw (`m1` divides `dim_z`; `m2` power of two dividing `dim_x`, `dim_y`; `m3` <= 16 dividing both).
4. CUDA needs `dim_x == dim_y`, multiples of 64 and an in-place transpose (it only logs an error/warning). Port: out-of-place transposes, any dimensions.
5. PBA assumes that the obstacle stored in a voxel after phase 1 lies in the voxel's own (x, y) column; a map that already went through a distance computation violates this, so CUDA PBA is only valid on a cleared map. Port: a first pass resets every voxel that does not store its own position.
6. Obstacle insertion of any meaning except `eBVM_OCCUPIED` prints an error and un-marks the voxel; port: throws. `mergeOccupied` takes an unsigned `offset` that only changes the stored coordinates (never the target index) and does no bounds check; port: no offset, dimensions must match.
7. `getObstacleDistance` returns an `int` (truncated root); `INT_MAX` for uninitialised voxels gives 46340.
8. The CUDA 3-phase comparisons are done in float (`devicePBAintersection3DY`); with 10-bit integer coordinates this cannot change a distance (a misjudged boundary is within 1e-4 of an integer position where both candidates are equally near); the tests found no mismatch.

## Limits
- <= 1023 voxels per axis; the exact lines are processed by one invocation with private arrays of 1024 entries; `m3` <= 16 (work group of 16 x 16).
- Memory: map + 4 temporary buffers of the map size (Exact: 2 pairs of cost/site; PBA: stack, forward pointers, transposed copy).
- Pipelines are created per map object (PBA pipelines on first use); host reads of single voxels (`squared_obstacle_distance`) cost ~3.5 ms each because `DeviceBuffer::download` creates a staging buffer per call - use the batch queries.

## Verification (2026-10-23, Intel UHD, validation layer on, zero validation errors)
- Reference: `tests/reference/distance_map_reference.h` - obstacle set + brute force over all obstacles (what CUDA `exactDistances3D` does), independent of both algorithms; ties are not specified, so a voxel passes if its stored site is an obstacle at the minimal distance.
- 23 tests: `test_distance_voxel_map.cpp` (construction incl. 1023 limit, insertion of points / coordinates / meta clouds with outside counts and meaning errors, single obstacles in many shapes, random obstacles in six shapes (flat, thin, 1-voxel axes), ties and full maps, empty maps, repeated computation, axis length 1023, queries incl. truncation and range errors, `extract_distances` for seven radii incl. cap and borders, `merge_occupied` for six thresholds, a 1 M voxel map) and `test_distance_pba.cpp` (single band in eight shapes, band combinations in 14 configurations, every valid (m1, m2, m3) on 32^3 = 150 x 2 runs, empty bands and special layouts (plane, wall, diagonal, corners), agreement with Exact, recompute / mixing algorithms, axis length 1023, invalid band counts, tall maps, performance report).
- **Mutation testing, 71 mutations (shaders and C++): 69 killed, 2 result-equivalent.** Covered: insertion bounds / stored value / counters / input kind, merge threshold and coordinates, every line of the z pass and of the line envelope (cost, stale-site handling, separation, line mapping and length, envelope start/pop/limit), `extract_distances` rules, queries, the PBA sanitising pass, flood (band top, uninitialised distance, stores), inter-band propagate/update (targets, comparisons, sentinel handling), stack back pointers / tail pointer / envelope test / intersection formula, forward pointers, band merging (head and tail pointers, kept counter limit, back pointer of band 2), phase 3 (envelope walk, rounds, shared state), transposes, and the C++ glue (algorithm selection, validation of m1/m2/m3, dimensions of both passes and of the transposes, thread counts, group counts, threshold conversion, input kinds, rounding of the root). The two equivalent mutants only change speed: publishing the shared stack state from the first instead of the last row of a work group in phase 3 (the next round just pops more entries), and the lower bound of the kept counter in band merging (the loop only runs longer). Mutation testing also removed three redundant code paths that could not be killed: a floor division whose numerator is never negative, a sentinel guard for the forward flood result (an uninitialised forward result can never win against a valid obstacle) and a final-pass flag of the line shader (positions without obstacles already receive the uninitialised site). One survivor was a badly chosen mutant (an extra, idle work group in phase 3 is harmless) and was replaced by one that drops columns; separately, a stale cache in the reference helper (found by the tall-map test) was fixed.
- Whole suite: `test_vulkan` 132 cases pass; `ctest` in `build/verify-vk` 140 of 141 pass (K18 pre-existing), CPU-only build unchanged (8 of 9).
